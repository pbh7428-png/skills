# 결과물 독립 검토

결과물을 다른 에이전트가 독립적으로 살피고, 원래 에이전트가 지적의 타당성 판단과 후속 처리를 책임진다. 에이전트는 작업을 맡아 수행하는 별도 AI를 뜻한다. 다른 회사나 다른 모델을 반드시 사용할 필요는 없다. 다른 스킬 없이 사용할 수 있다.

사용자 설명과 새 Markdown 문서는 기본적으로 한글로 쓰되 지정한 언어를 우선한다. 필요한 기술 용어는 쉬운 뜻과 함께 설명한다.

## 범위와 실행 경계

- 검토만 요청받았다면 결과까지 보고하고 작업 파일은 수정하지 않는다. 수정까지 맡았다면 타당한 지적의 수정과 관련 검증까지 진행한다. 이미 맡긴 구현 작업의 일부로 검토한다면 기존 범위 안에서 후속 처리를 수행한다.
- 사용자의 확정된 결정·제외 범위와 프로젝트 규칙을 존중한다. 검토를 이유로 기획에서 구현으로 넘어가거나 사용자 결정을 임의로 바꾸지 않는다. 스킬은 권한을 추가하거나 현재 실행 모드를 바꾸지 않는다.
- 모든 작은 편집에 별도 검토를 붙이지 않는다. 사용자에게 제시할 실행 계획의 검토는 이 스킬의 대상이 아니다. `plan-review`가 있다면 그 역할로 구분하며, 없어도 이 스킬의 결과물 검토는 가능하다.
- 정상적인 실행 경로가 막히거나 실패해 다른 도구·계정·인터페이스·경로로 우회하려면, 먼저 막힌 이유·제안 방법·변경 범위와 영향을 설명하고 명시적 허가를 받는다. 작업 완료 요청이나 Full Access를 우회 허가로 간주하지 않는다. 허가 대기 중에는 우회와 무관한 일을 계속할 수 있으며 상위 지침의 금지는 유지한다.

## 1. 검토 범위와 자료 준비

현재 요청과 기존 자료에서 다음을 정리한다. 이미 확인할 수 있는 내용은 다시 묻지 않고, 검토 판단에 중요한 정보가 빠졌을 때만 질문한다.

- 사용자 요구, 확정된 결정, 중요한 제약과 제외 범위.
- 검토할 원본의 위치와 범위, 충족해야 할 요구사항·평가 기준.
- 코드의 변경 전후 또는 변경 내역. Git이 없다면 관련 파일과 변경 설명.
- 기존 검증 결과와 증거의 위치, 수행하지 못한 확인.

작성자의 자기 평가나 대화 전체를 기본 입력으로 넘기지 않는다. 필요한 사용자 결정은 생략하지 않는다. 리뷰어가 관련 원본을 추가로 읽을 수 있게 하고, 현재 변경과 연결되는 자료부터 확인하도록 범위를 정한다.

## 2. 별도 에이전트의 독립 검토

사용 가능한 에이전트 도구로 리뷰어 1명을 기본 호출한다. 새 대화 맥락에 필요한 자료와 역할만 전달한다. 도구가 대화 이력 상속을 조절할 수 있다면 전체 이력을 넘기지 않는 방식을 사용한다. 아래 역할·판단 기준·반환 내용을 검토 요청에 포함한다.

**리뷰어의 역할**

- 원본과 필요한 관련 자료를 직접 읽고 검토한다. 전달받은 요약만으로 결론을 확정하지 않는다.
- 작업 파일과 프로젝트 상태를 직접 변경하지 않고 지적과 개선 방향을 반환한다. 검증 실행이 필요하면 허용 범위와 파일 생성·외부 연결 등의 부작용을 먼저 확인한다. 권한이 없으면 원래 에이전트에게 필요한 확인을 제안한다.
- 다시 다른 리뷰어를 생성하거나 이 검토 절차를 중첩 호출하지 않는다. 이미 리뷰어 역할로 이 스킬을 읽었다면 이 단계의 검토만 수행하고 반환한다.

**대상에 맞춰 선택할 관점**

| 대상 | 주요 확인 사항 |
| --- | --- |
| 기획·설계·평가 기준 문서 | 목적과 설계의 연결, 누락·모순, 구현 가능성, 확인 가능한 기준인지 |
| 구현 코드 | 요구 충족, 실제 오류 조건, 기존 동작 영향, 관련 테스트와 검증의 충분성 |
| 결과물·평가 보고서 | 평가 기준 충족, 결론을 뒷받침하는 증거, 확인하지 못한 부분 |
| 검증 후 개선 내용 | 원래 문제 해결 여부, 새 문제 발생 여부, 범위를 벗어난 변경 |

**반환할 내용**

- 지적은 가능한 범위에서 **문제 위치 / 발생 조건 또는 사례 / 영향 / 근거 / 개선 방향**을 담는다. 파일·구간·요구사항 등 다시 확인할 수 있는 위치를 사용한다.
- **중대 문제 / 일반 문제 / 선택적 제안**을 실제 영향에 따라 구분한다. 확인된 결함과 추가 확인이 필요한 의문도 구분한다. 중대 문제는 핵심 요구·결과의 신뢰성 등에 큰 영향을 주는 문제다.
- 문제 개수나 점수를 채우지 않는다. 문체·취향 차이를 결함으로 제시하지 않는다. 문제가 없다면 확인 범위 안에서 그렇게 말하고, 미확인 부분과 검토 한계를 함께 남긴다.

독립 에이전트를 사용할 수 없거나 호출에 실패하면 독립 검토를 완료했다고 주장하지 않는다. 제한과 남은 검토를 알리고, 다른 도구 등을 이용한 우회는 사전 허가를 받는다. 허용된 자체 검토를 했다면 그 결과를 독립 검토와 분명히 구분한다.

## 3. 지적 확인과 후속 처리

원래 에이전트는 리뷰어의 지적을 검증할 주장으로 다룬다. 관련 요구·원본·변경·실제 증거를 확인하고 필요하면 허용된 범위에서 문제를 재현한다. 지적을 자동 수용하거나 근거 없이 반박하지 않는다.

- 지적을 **반영 / 미반영 / 보류**로 처리한다. 중요한 미반영·보류에는 근거와 영향을 남긴다. 근거가 부족한 의문을 확인된 결함으로 바꾸지 않는다.
- 검토만 요청받았다면 수정 제안과 판단을 보고하고 파일을 변경하지 않는다. 수정이 맡겨진 범위 안이면 원래 에이전트가 필요한 부분을 고친다. 범위를 넘어서는 결정은 사용자에게 확인한다.
- 수정한 부분과 영향을 받는 동작을 적절히 확인한다. 코드라면 관련 테스트나 실제 동작, 문서라면 요구와의 일치·연결·모순 등을 확인한다. 관계없는 검사나 형식적인 테스트를 늘리지 않는다.
- 수정 전 실행 결과를 수정 후의 증거로 쓰지 않는다. 검토 의견이나 문서 확인을 실제 실행 검증으로 표시하지 않는다. 평가 결과에 맞춰 통과 기준을 조용히 낮추지 않는다.

## 4. 검토 반복과 보고

기본은 **리뷰어 1명, 최초 검토 1회**다. 중대한 지적을 수정했거나 핵심 내용이 바뀌었다면 바뀐 부분과 연결 지점 중심으로 **추가 독립 검토 1회**를 수행한다. 사소한 문구 수정마다 재호출하지 않는다. 규모나 사용자 요청에 따라 조절하되 이유 없이 인원과 횟수를 늘리지 않는다.

동일 대상·동일 변경의 검토는 재사용한다. 기본 제한에 도달하면 새로운 리뷰어 호출을 자동 반복하지 않고 미해결 문제·영향·다음 선택지를 보고한다. 제한은 필요한 수정과 실제 검증을 생략하라는 뜻이 아니다. 새 단계나 범위는 구분하되 이름만 바꿔 반복 제한을 우회하지 않는다.

사용자에게 중요한 지적과 처리 결과, 실제 확인 결과와 증거, 남은 한계를 간결하게 전달한다. 검토만 한 경우 수정 제안임을 분명히 한다. 계획한 확인·실제 수행한 확인·수행하지 못한 확인을 구분하고, 미해결 문제를 통과로 표시하지 않는다. 검토 완료를 사용자 승인으로 간주하지 않는다. 작은 문구 수정까지 별도 처리표나 보고서를 만들거나 검토 대화 전체를 출력하지 않는다.
