# PRD + TRD 작성 (시험용)

## 입력 (모두 있어야 시작)
- `docs/01_requirements_table.md` — README 추출표
- `docs/interview.md` — HR 인터뷰 결과, 확정 조건, KPI 우선순위
- `docs/02_data_check.md` — 데이터 예외, 검증불가 조건
없는 파일이 있으면 무엇이 없는지 알리고 멈춘다.

---

## PRD → `docs/PRD.md`

1. **문제와 동기**: 왜 하는가. HR이 말한 현장 불만·페인포인트 포함
2. **범위 (MoSCoW)**: Must / Should / Could / Won't
   - 각 항목에 요구ID와 출처(README 위치 또는 인터뷰 Q번호)
   - Won't는 제외 이유 명시
3. **제약**: Hard constraint / Soft constraint 구분
   - Soft는 처리 방식 명시: KPI로 측정 / 목적함수 패널티 / 향후 과제
4. **KPI**: 우선순위 순서, 정의(계산식), baseline 정의
5. **가정 목록**: 질문하지 않았거나 답을 못 받은 항목의 처리 가정
6. **엣지 케이스 처리 방침**: 데이터 예외, 수요 0/급증, 고장, 용량 초과 등
7. **수용 기준**: 요구ID마다 테스트 가능한 문장 1개 이상
   - 결과물 조건(데이터 검사 ③ 유형) 반드시 포함
   - 형식: `AC-{n} (REQ-{id}): {입력/상황}일 때 {결과}가 {측정 가능한 기준}`

---

## TRD → `docs/TRD.md` (1페이지 제한)

1. **모듈과 입출력 계약**: 모듈 3~5개, 각 모듈의 입력/출력 파일과 스키마(열 이름·타입) 고정
   - 맨 앞은 데이터 검증 모듈 (h-data-check 코드 재사용)
   - 맨 끝은 KPI 평가 모듈
2. **교체 가능 구조**: 모듈마다 `mvp` 구현과 `improved` 구현이 **같은 인터페이스**를 쓰고, 설정값 하나로 전환
3. **MVP 단계 vs 개선 단계**: 모듈별로 MVP에 쓸 단순 방법과 개선 방법을 표로
   - MVP 목표: 모든 모듈이 입력→출력 end-to-end 연결, 샘플 데이터로 실행, 핵심 수용 기준 통과
4. **알고리즘 선택**: 선택 + 대안 + 이유 (→ h-decision-log에 그대로 기록)
5. **테스트 전략**: 모듈 테스트 / e2e 테스트 / 수용 기준 테스트 / 데이터셋(정상 샘플, 엣지셋, 대규모)
   - MVP 결과 KPI = baseline
6. **개선 백로그**: 우선순위, 예상 효과, 의존성, **병렬 가능 여부** 표시

---

## 마지막: 자가 누락 체크
입력 3개 파일에 있는데 PRD/TRD에 반영 안 된 항목을 나열한다. 없으면 "누락 없음"과 근거(매핑 표)를 출력.

## 금지
- 장황한 서술, 일반론
- TRD에 구현 코드 작성
- 입력에 없는 요구사항 추가 (필요하면 '가정'으로)
