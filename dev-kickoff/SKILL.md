# 개발 시작 챙기기

구현 전에 무엇을 왜 만들지, 어떻게 만들지, 요구를 충족했는지 어떻게 확인할지 연결한다. 문서의 분량은 프로젝트 규모에 맞추고, 이미 정한 내용은 다시 묻지 않는다. 사용자 설명과 새 Markdown 문서는 기본적으로 한글로 작성하되 사용자가 지정한 언어를 우선한다. 필요한 기술 용어는 뜻과 배경을 쉽게 설명한다.

## 대전제 — 우회 실행 전 사전 허가

정상적인 실행 경로가 막히거나 실패해 다른 도구·계정·인터페이스·경로로 우회하려는 경우, 실행 전에 사용자에게 막힌 이유, 제안하는 우회 방법, 변경 범위와 영향을 설명하고 명시적인 허가를 받는다. 작업 완료 요청이나 Full Access 설정만으로 우회를 허가받았다고 간주하지 않는다. 허가를 기다리는 동안 우회와 무관한 작업은 계속할 수 있다. 사용자의 허가가 있더라도 상위 지침에서 금지한 제한 우회는 수행하지 않는다.

## 진행 방식

1. **문제 정의:** 대화와 기존 문서에서 사용자, 사용 상황, 해결할 문제, 기대하는 결과를 정리한다. 기능 목록만 있을 때는 그 기능으로 어떤 결정을 하거나 일을 끝내려는지 확인한다.
2. **가능성 확인:** 핵심 기능에 필요한 데이터·API(외부 서비스 연결 방법)·권한·실행 환경을 확인한다. 불확실한 핵심 의존성부터 살피고, 자료의 존재와 사용 가능성을 구분한다. 읽기나 작은 실험은 맡겨진 범위와 현재 권한·실행 모드 안에서 수행한다. 확인하지 않은 내용은 가정 또는 미정으로 남긴다.
3. **PRD — 무엇을 왜 만드는가:** 사용자·문제·사용 흐름, 첫 버전 필수 기능, 제외 범위, 관찰 가능한 성공 기준을 정한다.
4. **TRD — 어떻게 만드는가:** 실행 환경, 구성 요소와 데이터 흐름, 데이터 출처·저장·갱신 방법, 핵심 규칙과 오류 처리를 정한다. 선택에 실제 영향을 주는 기술 대안과 선택 이유만 남긴다.
5. **평가 Spec — 요구를 충족했는지 확인할 기준:** 아래 원칙에 따라 요구사항과 확인 방법을 연결한다. 구현 전에 기준을 정하되, 검증 실행은 맡겨진 범위와 현재 지침에 따른다.
6. **다음 작업으로 연결:** 확정 사항, 중요한 가정·미정 사항과 첫 구현 단위를 공유한다. 사용자가 구현까지 요청했고 핵심 불확실성이 해소됐으면 현재 실행 모드에 맞게 이어간다. 기획만 요청받았다면 기획 결과물을 전달한다.

## 질문과 결정

- 내용을 **확정 / 가정 / 미정**으로 구분한다. 근거 없는 가정을 확정된 요구사항처럼 쓰지 않는다.
- 답에 따라 목적·범위·핵심 구조가 달라지는 사항을 우선해 묻는다. 한 번에 중요한 질문 1~3개를 묶고, 가능한 경우 선택지를 제시한다.
- 기존 대화나 프로젝트에서 답을 찾을 수 있으면 직접 확인한다. 사소하고 되돌릴 수 있는 선택은 판단해서 진행하고 필요한 가정을 알린다.
- 필수 답을 기다리는 동안 독립적으로 할 수 있는 조사와 정리를 계속한다. 미정 사항에 의존하는 구현은 답이 올 때까지 진행하지 않는다.
- 문서 작성을 일률적인 추가 승인 절차로 만들지 않는다. 스킬은 작업 범위나 권한을 추가로 부여하지 않으며 현재 실행 모드를 바꾸지 않는다.

## 평가 기준 작성

기본 연결은 **요구사항 → 확인할 상황과 입력 → 기대 결과 → 통과 기준 → 확인 방법**이다. 표나 짧은 문장 등 이해하기 쉬운 형태를 선택한다.

- 기대 결과는 보여야 할 동작·결과, 통과 기준은 그것을 충족했다고 판단할 조건이다. "잘 작동한다"처럼 판정할 수 없는 표현을 피한다.
- 정상 사례와 오류·누락·경계 상황 중 관련 있는 것을 고른다. 모든 가능한 상황을 열거하지 않는다.
- 확인 방법은 자동 테스트, 실제 사용 흐름 확인, 표본 검토, 사용자 평가 등 목적에 맞게 정한다.
- AI 결과를 평가한다면 대표 입력과 까다로운 입력을 정하고, 정답이 하나가 아닐 때는 어떤 근거로 품질을 판단할지 설명한다. 예를 들어 요약 도구라면 주요 날짜·금액 유지와 원문에 없는 사실 추가 여부를 원문과 비교한다.
- 처리 시간·비용·개인정보·사람의 확인 과정은 관련 있을 때 추가한다. 근거 없는 품질 목표나 수치를 만들지 않고, 임시 목표는 가정과 근거를 명시한다.
- 요구사항이나 기준이 바뀌면 관련 PRD/TRD와 평가 기준을 함께 갱신하고 중요한 변경 이유를 남긴다. 나온 결과에 맞춰 통과 기준을 조용히 낮추지 않는다.
- 계획한 확인, 실제 수행한 확인과 그 증거, 확인하지 못한 부분을 구분한다. 문서 검토를 실행 검증으로 간주하지 않는다.

## 최소 문서와 인계

**이 스킬의 결과물은 다른 사람이나 AI가 이해하고 이어서 활용하기 쉬운 형태로 작성한다.** 원래 대화 전체를 다시 읽지 않아도 목적, 확정 사항, 중요한 가정·미정 사항, 검증 기준과 다음 작업을 파악할 수 있게 한다.

기존 기획·설계·평가 문서가 있으면 위치와 명칭을 존중해 갱신한다. 작은 프로젝트는 `docs/planning.md` 하나에 합친다. 분리가 이해와 관리에 도움이 될 때만 문서를 나누며 고정된 파일명이나 양식을 강제하지 않는다. 프로젝트 폴더가 정해지지 않았거나 파일 작성이 허용되지 않는 모드라면 대화에서 초안을 정리한다.

- PRD에는 목적·사용자·사용 상황, 주요 사용 흐름, 필수 기능·제외 범위, 성공 기준을 담는다.
- TRD에는 실행 환경·주요 구성 요소, 데이터 출처·확보 가능성·저장·갱신 방법, 데이터 흐름·핵심 규칙·계산식·오류 처리, 중요한 기술 선택과 이유를 담는다.
- 평가 기준에는 요구사항별 상황·입력·기대 결과·통과 기준·확인 방법을 담는다. 별도 문서가 없어도 각 요구와 기준의 연결을 알 수 있게 한다.
- 명확한 제목과 일관된 용어를 사용한다. 관련 자료·파일의 위치와 중요한 결정의 근거를 필요한 만큼 남기고, 여러 문서는 관련 부분을 서로 연결한다. 자료를 연결하더라도 핵심 결정은 결과물 자체에서 이해할 수 있게 한다.
- "앞에서 정한 방식"처럼 대화에만 의존하는 표현을 피한다. 다음 작업과 이를 막는 중요한 미정 사항을 구체적으로 남긴다.
- 빈 항목, 관계없는 내용, 중복 문서나 인계 전용 보고서를 형식적으로 만들지 않는다.

## 특히 먼저 확인할 것

- 로컬 실행인지 온라인 배포인지, 설치와 네트워크가 필요한지 확인한다. 이전 프로젝트의 선택을 새 프로젝트에 자동으로 강제하지 않는다.
- 점수·순위·비용·효율을 보여주는 제품은 각 지표의 의미, 단위, 계산식과 비교 가능성을 구현 전에 정한다. 숫자의 형식이 같다는 이유로 서로 다른 측정값을 합치지 않는다. 대체 지표를 쓰면 무엇을 대신 측정하는지 설명한다.
- 요청한 대상이나 설정 중 데이터가 없는 경우를 따로 설계한다. 누락을 0점으로 표시하거나 다른 조건의 값을 대신 쓰지 않는다.
- UI(사용자가 보는 화면) 요구사항은 필요한 경우 간단한 스케치나 구체적인 예로 해석을 맞춘다.
